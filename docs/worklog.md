### 14:10頃 1手を指す（01-1）

- インターフェースの案は3つ：A `board.move(2)` で盤面を書き換える、B `Board().move(2)` が新しい盤面を返す、C `Move(2).apply(board)`。
- テストはサンプルコードであり、クライアントにとって使いやすいかを判断する場と考える。
- B は「Board は immutable」という設計をクライアントに見せることになる。
- メンタルモデル：手を打つたびに新しい盤面が現れるのか、1つの盤面の上で石が動いていくのか。どちらもありうる。お題は「初期盤面から1手を指したあとの盤面を求めます」と書いているので、前者が素直。B にした。
- C は内部実装で現れるかもしれない。
- immutable をクライアントへの約束にするなら、それはお題で決まっていない決定なので、テストとして残す。TODO に「1手を指しても元の盤面は変わらない」を足した。
- 4パターン（穴2、5、7、8）は最初から parametrize にせず、穴2の1件から始める。
- 穴2の Red に対して、仮実装でも Board を任意の石の数で作る必要があると気づいた。
- 明白な実装は内部表現によってロジックが大きく変わるので、まず三角測量にしようと考えた。
- やっとむの提案：Board に「ある穴から別の穴へ石を1つ移す」メソッドを加え、move() はそれを使う。move() は「どの穴から石をどう移すか」というルールを表す。内部表現に触れるのは石を1つ移すメソッドと stones() だけになり、内部表現を決めるのを遅らせられる。
  - 名前は `move_a_stone()`。お題の用語にない新しい概念。
  - immutable の方針に合わせ、`move_a_stone()` も新しい盤面を返す。パフォーマンスは気にならない。
  - コピーには `copy()` メソッドを新設する（Python にはコピーコンストラクタはない）。
  - 公開するかどうかに強い意志はない。あとで役に立ちそうなので公開にしておく。
- 穴2のテストは一時的に skip し、TODO では `move_a_stone()` を先にやる項目に入れ替えた。
- `move_a_stone()` は list を使う明白な実装にした。`copy()` は直接のテストを書かず、`move_a_stone()` を通じて使う。`stones()` は内部の list ではなくコピーを返す。
- Green のコミット時、skip 中の穴2のテストに mypy が `"Board" has no attribute "move"` を出していたのに、そのままコミットしてしまった。skip は実行を止めるだけで型チェックは止めない。`# type: ignore[attr-defined]` で一時的に無視し、skip を外すときに消す。
  - Claude のコマンドが、チェックの失敗でコミットを止める組み方になっていなかった。
- 「真に immutable」と「公開 API で immutable に振る舞う」の違いを整理した。後者に決めた → [ADR 0005](adr/0005-board-behaves-immutable.md)
- README の ADR 一覧に 0004 が抜けていたので、0005 と一緒に足した。
- `move_a_stone()` の Refactor はなし。穴番号から添字への変換（`- 1`）が2回出てくるのは気になる。`__getitem__`/`__setitem__` を持つ穴の並びのクラス（`Pits`）を作れば `pits[2] += 1` と書けるが、変換は `move_a_stone()` の中に閉じられるかもしれないので、今はこのまま。
- 次のサイクルとして、穴2のテストの skip を外した。
- `move()` は `move_a_stone()` を石の数だけ繰り返す明白な実装にした。8から1に回る処理はまだ入れていない。
